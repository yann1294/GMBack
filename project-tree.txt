- The DTOs will be used only for reponse and request validation. They would not have constructors, only accessors.
 Help transfer only necessary data to avoid security leak,to prevent network overhead,
 avoid heavily loaded request where we transfer the unnecessary data around again and again.
 With DTOs, we can build different views from our domain models, allowing us to create other representations of
 the same domain but optimizing them to the client’s needs without affecting our domain design.
 Such flexibility is a powerful tool to solve complex problems.
    - TourDTO will be broken down into -> TourLocationDTO, UserDTO, ActivityDTO
- Entities will be used when persisting data (database).
- Services: Will contain business logic... any processing or algorithms
- VO (view object): Defines the data structure of data to be moved within the application. They are the actual
 domain objects.
- Types would be used to shape all models such as VO & entities

Has getters and setters:
- All VOs will have getters and setters


To ensures clear separation of concerns, simplifies maintenance, and avoids unnecessary complexity 
   DTO: Fully leverage @Expose, @Exclude, and related decorators for serialization/deserialization 
      to ensure data is correctly mapped to/from external APIs.
   Entity: Use decorators sparingly, mainly focusing on persistence-related concerns 
      (e.g., @Column, @PrimaryGeneratedColumn from ORM libraries). Use @Expose only for special cases like logging or diagnostics.
   VO: Avoid @Expose and similar decorators here. Keep VOs focused on domain logic and ensure 
      they act as simple, encapsulated objects for internal use.


Keep input DTOs (CreateXDTO, UpdateXDTO) focused on validation and structure for input operations.
Keep output DTOs (ResponseDTO) focused on presenting data to the client, which may involve transformations or derived fields.
   ResponseDTO is meant to represent a broader concept that isn’t tied specifically to creation, extending the base UserDTO is better.
   Especially useful if there are additional derived fields (e.g., fullName) or if the response format is significantly different.


Composition vs Aggregation
   To show tight coupling (Composition):
   Create the associated object internally in the constructor or methods.
   Prevent external reassignment of the associated object by making it private or readonly.
   Automatically delete the associated object when the parent object is deleted.

   To show loose coupling (Aggregation):
   Pass the associated object as an external dependency.
   Allow the associated object to be shared or replaced independently.
   Ensure the associated object’s lifecycle is independent of the parent.

REST or NOT
   The public-facing API uses RESTful principles to expose CRUD endpoints. These endpoints delegate specific tasks to the GuideService.
   The internal service (e.g., AdminService) receives encapsulated domain objects (GuideVO) for more complex operations, ensuring rich business logic 
   without exposing internal workings to external users.

   For simple, RESTful operations, stick with @Param('uid').
   For complex scenarios or when additional context might be needed, use the body approach (adminVo.getuid()).
   Validation can be applied to either @Param or @Body using pipes, ensuring robust data handling.

Use async/await only where necessary.
   Avoid wrapping synchronous logic in async unnecessarily.
   Adding async unnecessarily makes the function always return a promise. Avoid using async for functions meant to return simple synchronous values.
   Prefer concise direct returns for simple functions.
   Understand the Flow:
      Know whether tasks need to run sequentially (await) or can run concurrently (Promise.all).
      Use async/await to enhance readability, especially when handling complex asynchronous workflows.
   Performance Awareness:
      For performance-critical tasks, ensure you aren't inadvertently slowing down operations by enforcing sequential execution when parallelism is acceptable.


Processes (through containers):
- guide creation
- guide assignment
- booking : start from User Management (selecting tour or package), goes through Tour Management
  (tour or package creation, guide assignment) and booking (core business logic of booking), ends at paymnent
- authentication
- logging
- payment


Assumptions and Constraints for Beta version:
- This structure balances modularity with maintainability and follows a clean, scalable design.
- Guides are by default assigned to tours/packages
- A user will log in then he will be redirected to the user management space.
   From there, he can book tours or packages.
   After booking a tour, the flow of the app will to go to the tour management component.
   That is :
    - adding the user to the tour while he is waiting the confirmation from the guide.
    - Notifications will be sent to the guide so that he can accept the user.
   After the guide accepts the request from the user, a signal is sent to the user space allowing him to pay for the tour.
- Price could be static
